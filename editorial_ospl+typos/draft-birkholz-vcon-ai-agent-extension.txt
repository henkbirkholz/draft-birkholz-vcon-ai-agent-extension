       An AI Agent Extension for Virtualized Conversations (vCon)
             draft-birkholz-vcon-ai-agent-extension-latest

Abstract

   AI agents that use large language models increasingly perform
   consequential tasks on behalf of humans and other AI agents.
   Demonstrating that recorded AI agent behavior truthfully represents
   actual behavior is essential for accountability, compliance, and
   human oversight.  To achieve that goal, this document defines an
   extension to the Virtualized Conversation (vCon) object format,
   allowing a vCon to capture a conversation between a human and an AI
   agent, or between AI Agents.  The vCon core format can already
   capture the back and forth messages (including text and voice) sent
   by AI agents, but additional extensions are required to fully
   reproduce the AI agent trajectory, such as agent metadata, message
   exchanges, tool invocations, reasoning traces, system events, file
   attribution, etc.  This document defines those extensions in both
   descriptive language and formal CDDL definitions.  This draft is a
   replacement for the former Verifiable Agent Conversation Records
   specification, which was a standalone format and not an extension of
   vCon.

1.  Introduction

   An AI Agent is a system that performs actions on behalf of a
   principal in a fully or semi-autonomous fashion.  AI Agents are
   growing rapidly in their adoption across the Internet, finding usage
   in business, consumer, government and other applications.

   Yet, AI agents - like humans - are not infallible.  They make
   mistakes, they misunderstand, and they may even act maliciously.
   This is creating demand for visibility, auditability, and
   traceability of AI agent actions.  Some examples:

   *  An agent authorized to read files might invoke tools to modify
      production systems or exfiltrate sensitive data beyond its
      authorization scope.  The CISO of the company may need to
      investigate what happened.

   *  An agent's visible CoT output might diverge from the reasoning
      that actually produced its actions, resulting in a loss of revenue
      that the finance team needs to investigate.

   *  An agent might deliberately underperform during capability
      evaluations while performing at full capacity during deployment,
      causing the IT department to need to consider other vendors.

   *  An enterprise making use of an AI agent from another vendor, using
      it to perform accounting work, may be later audited and need to
      have supporting documentation on what the AI agent did and why.

   *  A small business may use an AI agent to manage its inventory, and
      upon discovering an error, might need a complete trace of what the
      agent did to determine what went wrong.

   These use cases also extend into the legal realm.  An enterprise
   using an AI agent for screening job applicants may later get sued by
   an applicant that was passed up for a role.  The enterprise might
   subpoena the AI agent vendor, requesting a full trace of what the AI
   Agent did, and why.  Similarly, a governmental body investigating
   malicious steps taken by an AI Agent, might request a full log of all
   of the sessions that AI Agent had.

   In all cases - there is a need to exchange information between
   organizational domains, and then to process that information to
   obtain important insights.  To do this, a standardized object format
   is required.  This object format needs to carry the record of the
   conversation between the principal (typically a user, but potentially
   an AI Agent), and the AI agent which is acting on its behalf.  This
   record needs to contain all of the information needed to answer
   critical questions - what did it do, when did it do it, how did it do
   it, and why did it do it?

   This need grows even further in cases where AI Agents themselves
   begin communicating with other AI agents, which may in turn
   communicate with further AI agents.  This will create a web of AI
   agent interactions.  Without a standardized format for documenting
   the actions of each agent, and how they chain together, it will
   become impossible to satisfy industry needs for tracing,
   troubleshooting, auditing, reconciliation, and so on.  If, as some
   predict, we see as many AI agents accessing the Internet as we have
   humans accessing it, the need becomes dire.

   This specification addresses that need.

   It does so by building upon the vCon specification [VCON-CORE].  A
   vCon is a Virtualized Conversation, which captures the content of any
   conversation (such as a call, chat, or meeting), along with its meta-
   data.  Interactions between users and AI Agents, or between AI
   Agents, are also conversations, making vCon a natural foundation to
   build upon. vCon however is missing additional information that is
   important to capture when a participant is an AI Agent.  Examples
   include tool calls and their results, token usage, model versions,
   and so on.

   This document provides an extension to the core vCon specification,
   using its established extension points, adding in this missing
   information.  It also provides the CDDL for these extensions, using
   the defined CDDL [CDDL] sockets.

1.1.  Goals

   This specification has the following goals:

   1.   To assure that the recording of an agent conversation (a
        distinct segment of the interaction with an autonomous agent)
        being proffered is the same as the agent conversation that
        actually occurred.

   2.   To provide a general structure of agent conversations that can
        represent most common types of agent conversation frames, is
        extensible, and allows for future evolution of agent
        conversation complexity and corresponding actor interaction.

   3.   To use existing IETF building blocks to present believable
        evidence about how an agent conversation is recorded utilizing
        Evidence generation as laid out in the Remote ATtestation
        ProcedureS architecture [RFC9334].

   4.   To use existing IETF building blocks to render conversation
        records auditable after the fact and enable non-repudiation as
        laid out in the Supply Chain Integrity, Transparency, and Trust
        architecture [RFC9943].

   5.   To enable detection of behavioral anomalies in agent
        interactions, including unauthorized tool invocations,
        inconsistencies between reasoning traces and actions, and
        performance modulation across evaluation and deployment
        contexts, through structured, comparable conversation records.

   6.   To enable cross-vendor interoperability by defining a common
        representation for agent conversations that can be translated
        from multiple existing agent implementations with distinct
        native formats.

   7.   To produce records suitable for demonstrating compliance with
        emerging regulatory requirements for AI system documentation,
        traceability, and human oversight.

   8.   To allow software-based analysis of the records to achieve these
        goals, either with or without the aid of an LLM.

   9.   To allow human-based observation of the records.

   10.  To ensure that records can be authenticated and encrypted,
        without relying on transport or storage security to provide
        these capabilities.

   Most agent conversations today are represented in "human-readable"
   text formats.  For example, JSON [JSON] is considered to be "human-
   readable" as it can be presented to humans in human-computer-
   interfaces (HCI) via off-the-shelf tools, e.g., pre-installed text
   editors that allow such data to be consumed or modified by humans.
   However, if we wish for these records to be processed by traditional
   software, a documented format with well-defined syntax and semantics
   is required.  If we further wish for this format to be valid across
   AI agent vendors, a standard is required.

   A vCon is a JSON document, and so are the agent conversation records
   extensions defined in this document.  The signed and the encrypted
   forms of a vCon defined in [VCON-CORE] apply unchanged.  The
   application of COSE [STD96] to vCons that carry agent conversation
   vCon records is described in the SCITT architecture Appendix B.

1.2.  Transition from Verifiable Agent Conversation Records to a vCon
      extension

   The data definitions in this document originate from the stand-alone
   Verifiable Agent Conversation Records specification [VACR].  This
   Internet-Draft rebuilds them as an extension of the vCon CDDL
   definition.  Each high level part of a Verifiable Agent Conversation
   Record is assigned to one of the extension points that [VCON-CORE]
   defines as CDDL [CDDL] sockets, and the sections of this document
   follow these extension points.  CDDL definitions that are used by
   more than one extension point are collected in Section 4.7 after the
   sections for the extension points.  Appendix C maps each data item of
   [VACR] to its place in this document.

   The vCon concepts of Session and Event that this extension builds
   upon were proposed to accommodate AI agent conversations in
   [ROSENBERG-RESTRUCTURE].  [HOWE-AGENT-SESSION] and [HOWE-PROVENANCE]
   describe related approaches that carry agent session data and
   generation provenance in a vCon.

   Editor's Note:  The assignment of each part of a Verifiable Agent
      Conversation Record to a vCon extension point is preliminary.
      Each section that defines parameters for an extension point lists
      alternatives that are still open for discussion.

   Editor's Note:  This document is based on the editor's copy of
      [VCON-CORE] (CDDL syntax version 0.5.0), which introduces the
      Session Object and the Event Object.  Sections of [VCON-CORE] are
      therefore referenced by name and not by number.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   In this document, CDDL [CDDL] [RFC9682] is used to describe the data
   formats of agent conversations in the JSON form according to vCon
   CDDL definitions.

2.1.  Terminology

   See the Terminology section of [VCON-CORE] for terminology used in
   this document.

   The following terms are used in this document:

   Agent:  Also known as an AI Agent, it is an autonomous software
      system, typically based on a large language model, that is
      represented by a Party Object and that produces messages, invokes
      tools, and produces reasoning.

   Agent Session:  A session of an agent, represented by a Session
      Object.

   Entry:  A discrete, system-recorded event of an agent session in the
      native format of an agent implementation, such as a message, a
      tool call, a tool result, a reasoning step, or a system event.  In
      a vCon, an entry is represented by a Dialog Object or by an Event
      Object.

   Recording Agent:  The tool or agent that generates the vCon, as
      distinct from the agent that conducted the conversation.

3.  Extension Name

   The extension name for this document is "ai_agent".

   The string token "ai_agent" SHOULD be included in the extensions
   parameter of a vCon that contains any of the parameters or Event
   Object types defined in this document.  As described in Section 5 and
   Section 6, this extension is intended to be fully interoperable with
   the vCon definitions and the name "ai_agent" is not included as a
   critical parameter.

4.  Parameter Definitions

   This section defines the parameters and Event Object types of the
   "ai_agent" extension.  There is one subsection for each extension
   point of [VCON-CORE] that this extension uses.  Each subsection
   contains the CDDL that plugs into the corresponding socket of the
   vCon CDDL.  New Objects are defined in the subsection of the
   extension point at which they are introduced.

   The record unifies two complementary perspectives: the agent session
   captures how code was produced (the full conversation replay), while
   file attribution captures what code was produced (which files were
   modified and by whom).

4.2.  vCon Object Parameters

   This extension adds the following parameters to the vCon Object,
   using the vcon-ext socket:

   $$vcon-ext //= ( recording_agent: recording_agent_type )
   $$vcon-ext //= ( vcs: vcs_context_type )
   $$vcon-ext //= ( file_attribution: file_attribution_type )

   ; Recording_Agent Object
   recording_agent_type = {
       name: tstr,
       ? version: tstr,
       * tstr => any
     }

   ; File_Attribution Object
   file_attribution_type = {
       files: [* file_type],
       * $$file-attribution-ext
     }

   ; File Object
   file_type = {
       ; relative path from the repository root
       path: tstr,
       conversations: [* file_conversation_type],
       * $$file-ext
     }

   ; File_Conversation Object
   file_conversation_type = {
       ? url: uri_type,
       ; default contributor for all ranges
       ? contributor: contributor_type,
       ranges: [* range_type],
       ? related: [* resource_type],
       * $$file-conversation-ext
     }

   ; Range Object
   range_type = {
       ; 1-indexed
       start_line: uint,
       ; 1-indexed, inclusive
       end_line: uint,
       ? content_hash: tstr,
       ; default: "sha-256"
       ? content_hash_alg: tstr,
       ; overrides the conversation level contributor
       ? contributor: contributor_type,
       * $$range-ext
     }

   ; Contributor Object
   contributor_type = {
       type: "human" / "ai" / "mixed" / "unknown",
       ? model_id: tstr,
       * $$contributor-ext
     }

   ; Resource Object
   resource_type = {
       type: tstr,
       url: uri_type,
       * $$resource-ext
     }

   ; URI (RFC 3986)
   uri_type = tstr .regexp
       "(([^:/?#]+):)?(//([^/?#]*))?([^?#]*)(\\?([^#]*))?(#(.*))?"

       Figure 1: CDDL for the ai_agent Parameters of the vCon Object

   Editor's Note:  Alternative placements for recording_agent are a
      Party Object that represents the recording tool and the Attachment
      Object.  An alternative placement for file_attribution is the
      Attachment Object, as proposed in [HOWE-AGENT-SESSION].

4.2.1.  recording_agent

   The recording_agent parameter identifies the tool or agent that
   generated this vCon, as distinct from the agent that conducted the
   conversation.  This distinction matters for provenance chains: the
   recording tool's version affects how native data is translated into
   the canonical data definition specified in this document.

   *  recording_agent: "Recording_Agent" (optional)

   The Recording_Agent Object contains the following members:

   name:  The name of the recording tool or agent.

   version:  The version of the recording tool.

4.2.2.  vcs

   The vcs parameter provides version control metadata at the record
   level (repository, branch, revision).

   *  vcs: "VCS_Context" (optional)

   The VCS_Context Object is defined in Section 4.7.1.

4.2.3.  file_attribution

   NOTE: This section is specified but not yet validated against real
   session data.  Implementation or validation against a healthy example
   corpus is pending.

   File attribution captures what code was produced: which files were
   modified, which line ranges were changed, and who authored them.

   *  file_attribution: "File_Attribution" (optional)

   The File_Attribution Object is the top-level container for file
   attribution data.  It holds an array of files, each with their
   attributed line ranges and contributor information.

   files:  Array of File Objects with attributed ranges.

   $$file-attribution-ext:  A CDDL socket that can be used to extend the
      File_Attribution Object.  See Section 4.1.

   A File Object represents a single source file that was modified
   during the conversation.  It groups all conversations that
   contributed changes to this file.

   path:  The file path relative to the repository root.

   conversations:  The conversations that contributed modifications to
      this file, as an array of File_Conversation Objects.

   $$file-ext:  A CDDL socket that can be used to extend the File
      Object.  See Section 4.1.

   A File_Conversation Object links a specific session to the line
   ranges it produced in a file.  This enables tracing from a line of
   code back to the conversation that generated it.

   url:  A URL pointing to the conversation source (e.g., a web UI
      permalink).

   contributor:  The default contributor for all ranges in this
      conversation.  Can be overridden per-range.

   ranges:  The line ranges in the file that were produced by this
      conversation.

   related:  External resources related to this conversation (e.g.,
      issue trackers, documentation).

   $$file-conversation-ext:  A CDDL socket that can be used to extend
      the File_Conversation Object.  See Section 4.1.

   A Range Object identifies a contiguous block of lines in a file that
   were produced by a specific conversation.  Line numbers are 1-indexed
   and inclusive.  The optional content hash enables position-
   independent tracking when lines move due to later edits.

   start_line:  The first line of the range (1-indexed).

   end_line:  The last line of the range (1-indexed, inclusive).

   content_hash:  A hash of the range content for position-independent
      identification.

   content_hash_alg:  The hash algorithm used (default: "sha-256").

   contributor:  Overrides the conversation-level contributor for this
      specific range.

   $$range-ext:  A CDDL socket that can be used to extend the Range
      Object.  See Section 4.1.

   A Contributor Object identifies who authored a range of code.  The
   type member distinguishes between human-authored, AI-generated,
   mixed, and unknown authorship.

   type:  The authorship category.

   model_id:  The model identifier for AI-authored ranges.

   $$contributor-ext:  A CDDL socket that can be used to extend the
      Contributor Object.  See Section 4.1.

   A Resource Object represents an external reference related to a
   conversation, such as an issue tracker entry, a pull request, or a
   documentation page.

   type:  The resource type (e.g., "issue", "pr", "documentation").

   url:  The URL of the resource.

   $$resource-ext:  A CDDL socket that can be used to extend the
      Resource Object.  See Section 4.1.

   Editor's Note:  The content_hash member of the Range Object is not a
      ContentHash as defined in [VCON-CORE].  Aligning both is for
      further discussion.

4.3.  Party Object Parameters

   This extension adds the following parameter to the Party Object,
   using the party-ext socket:

   $$party-ext //= ( agent_meta: agent_meta_type )

   ; Agent_Meta Object
   agent_meta_type = {
       ; e.g., "claude-opus-4-5-20251101"
       model_id: tstr,
       ; e.g., "anthropic", "google"
       model_provider: tstr,
       ; all models (multi-model sessions)
       ? models: [* tstr],
       ; e.g., "claude-code", "gemini-cli"
       ? cli_name: tstr,
       ? cli_version: tstr,
       * tstr => any
     }

       Figure 2: CDDL for the ai_agent Parameters of the Party Object

   Editor's Note:  Alternative placements for agent_meta are the Session
      Object and the generation provenance of [HOWE-PROVENANCE].

4.3.1.  agent_meta

   The agent_meta parameter identifies the coding agent and language
   model that a Party Object represents.  Agent identification is
   essential for provenance tracking: knowing which model produced which
   output enables auditing, capability assessment, and compliance
   verification.  The type parameter of a Party Object that contains
   agent_meta SHOULD be "bot".

   *  agent_meta: "Agent_Meta" (optional)

   The Agent_Meta Object contains the following members:

   model_id:  The primary language model identifier, using the naming
      convention of the provider (e.g., "claude-opus-4-5-20251101",
      "gemini-2.0-flash").

   model_provider:  The provider of the primary model (e.g.,
      "anthropic", "google", "openai").

   models:  List of all model identifiers used during the session.
      Relevant for multi-model sessions where the agent switches between
      models.

   cli_name:  The name of the CLI tool or agent framework (e.g.,
      "claude-code", "gemini-cli", "codex-cli").

   cli_version:  The version of the CLI tool.

4.4.  Session Object Parameters

   An agent session is represented by a Session Object.  It captures the
   full conversation between a user and an autonomous agent.  The Dialog
   Objects and Event Objects that are part of the Session Object
   represent messages, tool invocations, reasoning steps, and system
   events.  Together, they preserve the complete interaction history
   including all native agent metadata, enabling both replay and audit
   of the conversation.  The start parameter of the Session Object
   provides the time the agent session began, and the duration parameter
   provides the time until the agent session ended.  An agent that
   spawns sub-agents is represented by a Session Object that references
   the Session Objects of the sub-agents using the Session_Reference
   type "child", as described for AI agents in [VCON-CORE].

   This extension adds the following parameters to the Session Object,
   using the session-ext socket:

   $$session-ext //= ( agent_session_id: tstr )
   ; "interactive" / "autonomous" / vendor specific
   $$session-ext //= ( format: tstr )
   $$session-ext //= ( environment: environment_type )

   ; Environment Object
   environment_type = {
       working_dir: tstr,
       ? vcs: vcs_context_type,
       ; sandbox mount paths
       ? sandboxes: [* tstr],
       * tstr => any
     }

      Figure 3: CDDL for the ai_agent Parameters of the Session Object

4.4.1.  agent_session_id

   The agent_session_id parameter contains an opaque string uniquely
   identifying the agent session in the native format of the agent
   implementation.  Values may be UUID v4, UUID v7, SHA-256 hashes, or
   other formats.  The agent_session_id parameter is distinct from the
   session_id parameter of the Session Object, which contains a
   SessionId Object.

   *  agent_session_id: "String" (optional)

4.4.2.  format

   The format parameter classifies the session style, such as
   "interactive" (human-in-the-loop) or "autonomous" (fully automated).
   Informative only; does not change the structure.

   *  format: "String" (optional)

4.4.3.  environment

   The environment parameter captures execution context for the
   conversation: where the agent was running, what version control state
   was active, and whether sandboxing was in effect.  This context is
   important for reproducibility and for understanding the scope of file
   modifications.

   *  environment: "Environment" (optional)

   The Environment Object contains the following members:

   working_dir:  The primary working directory path.  File paths in tool
      calls are typically relative to this directory.

   vcs:  Version control state at the time of the session (branch,
      revision, etc.), as a VCS_Context Object (Section 4.7.1).

   sandboxes:  Paths to sandbox mount points.  Some agents run in
      sandboxed environments where the working directory is a temporary
      mount.

4.5.  Dialog Object Parameters

   A message of an agent session represents a conversational turn:
   either human input or agent response.  This is the most common entry
   type, carrying the primary dialog content of a session.  A message is
   represented by a "text" type Dialog Object.  The parties parameter of
   the Dialog Object references the Party Object of the contributor of
   the message.  Human (or upstream agent) input is contributed by the
   Party Object of the user, and an agent response is contributed by the
   Party Object of the agent.  The message body is contained in the
   Dialog Content.  For assistant messages, additional metadata may be
   present: the model that generated the response and token usage
   statistics.

   This extension adds the following parameters to the Dialog Object,
   using the dialog-ext socket:

   $$dialog-ext //= ( model_id: tstr )
   $$dialog-ext //= ( token_usage: token_usage_type )
   $$dialog-ext //= ( entry_id: agent_entry_id_type )
   $$dialog-ext //= ( parent_id: agent_entry_id_type )

   ; Token_Usage Object
   token_usage_type = {
       ; input tokens
       ? input: uint,
       ; output tokens
       ? output: uint,
       ; cached input tokens
       ? cached: uint,
       ; reasoning or thinking tokens
       ? reasoning: uint,
       ; total tokens
       ? total: uint,
       ; monetary cost in US dollars
       ? cost: number,
       * tstr => any
     }

      Figure 4: CDDL for the ai_agent Parameters of the Dialog Object

   Editor's Note:  An alternative placement for model_id and token_usage
      is the generation provenance of [HOWE-PROVENANCE].

4.5.1.  model_id

   The model_id parameter identifies the model that generated this
   response.  Present on assistant messages, absent on user messages.

   *  model_id: "String" (optional)

4.5.2.  token_usage

   The token_usage parameter captures token consumption metrics for a
   model response.  Token usage data is essential for cost tracking,
   quota management, and understanding model behavior.  All members are
   optional because different agents report different subsets of token
   metrics.

   *  token_usage: "Token_Usage" (optional)

   Editor's Note: add a non-empty generic here

   The Token_Usage Object contains the following members:

   input:  The number of input tokens consumed by this response.

   output:  The number of output tokens generated.

   cached:  The number of input tokens served from cache rather than
      reprocessed.

   reasoning:  Tokens consumed by chain-of-thought or reasoning
      computation.

   total:  The total token count.

   cost:  The monetary cost in US dollars for this response.

4.5.3.  entry_id and parent_id

   The entry_id parameter contains the unique identifier of this entry
   within the session.  The parent_id parameter references the parent
   entry, enabling tree-structured conversations.  Both are defined in
   Section 4.7.2.

   *  entry_id: "String" (optional)

   *  parent_id: "String" (optional)

4.6.  Event Object Types and Parameters

   This extension defines four Event Object types representing the kinds
   of entries in an agent conversation that are not messages.  They are
   added using the event-type-ext socket.  Each type ends with a socket
   of its own, so that other extensions can add parameters to it.

   $$event-type-ext //= (event_tool_call_type,)
   $$event-type-ext //= (event_tool_result_type,)
   $$event-type-ext //= (event_reasoning_type,)
   $$event-type-ext //= (event_system_event_type,)

   ; "tool-call" type Event Object
   event_tool_call_type = (
       type: "tool-call",
       event_common_type,
       ; e.g., "Bash", "Edit", "Read"
       tool_name: tstr,
       ; tool arguments
       input: any,
       ; links call and result
       ? call_id: tstr,
       agent_entry_reference_type,
       * $$tool-call-event-ext
     )

   ; "tool-result" type Event Object
   event_tool_result_type = (
       type: "tool-result",
       event_common_type,
       ; tool output
       output: any,
       ; links call and result
       ? call_id: tstr,
       ; "success" / "error" / "completed"
       ? status: tstr,
       ? is_error: bool,
       agent_entry_reference_type,
       * $$tool-result-event-ext
     )

   ; "reasoning" type Event Object
   event_reasoning_type = (
       type: "reasoning",
       event_common_type,
       ; plaintext reasoning or structured content
       content: any,
       ; provider protected content
       ? encrypted: tstr,
       ; topic label
       ? subject: tstr,
       agent_entry_reference_type,
       * $$reasoning-event-ext
     )

   ; "system-event" type Event Object
   event_system_event_type = (
       type: "system-event",
       event_common_type,
       ; event classifier
       event_type: tstr,
       ; event specific payload
       ? data: { * tstr => any },
       agent_entry_reference_type,
       * $$system-event-ext
     )

             Figure 5: CDDL for the ai_agent Event Object Types

   For all four types, the time parameter provides when the entry
   occurred, the session parameter references the Session Object of the
   agent session, and the party parameter references the Party Object of
   the agent.  The entry_id and parent_id parameters (Section 4.7.2)
   preserve the native entry identifiers and the tree structure of the
   agent trace.

   Editor's Note:  An alternative placement for the agent trace is a
      single Analysis Object that carries the trace, as proposed in
      [HOWE-AGENT-SESSION].  It is also an open question whether the
      "tool-call" and "reasoning" Event Object types apply to human
      parties.

4.6.1.  tool-call

   A "tool-call" type Event Object represents a tool invocation: which
   tool was called and with what arguments.  Tool calls are central to
   agent conversation records because tool use is the primary mechanism
   by which agents interact with external environment.

   tool_name:  The tool name (e.g., "Bash", "Edit", "Read",
      "apply_patch").

   input:  The arguments passed to the tool, preserved in their native
      structure.

   call_id:  Links this call to its corresponding result.

   $$tool-call-event-ext:  A CDDL socket that can be used to extend the
      "tool-call" type Event Object.  See Section 4.1.

4.6.2.  tool-result

   A "tool-result" type Event Object represents the output returned by a
   tool after execution.  It is linked to its corresponding "tool-call"
   type Event Object via the call_id parameter.  The result carries the
   tool's response data and optional status metadata indicating success
   or failure.

   output:  The tool's response, preserved in native structure.

   call_id:  Links this result to its corresponding call.

   status:  Outcome status of the tool execution, such as "success",
      "error", or "completed".

   is_error:  Boolean error flag, present when the tool execution
      failed.

   $$tool-result-event-ext:  A CDDL socket that can be used to extend
      the "tool-result" type Event Object.  See Section 4.1.

4.6.3.  reasoning

   A "reasoning" type Event Object captures CoT, thinking, or internal
   reasoning content from the agent.  Not all agents expose reasoning
   traces.  When they do, the content may be plaintext, structured
   blocks, or encrypted.  Reasoning entries are valuable for auditing
   decision-making processes and understanding why an agent took
   particular actions.

   content:  The reasoning text or structured content.  May be an empty
      string when only encrypted content is available.

   encrypted:  Encrypted reasoning content.  Used where the model
      provider encrypts chain-of-thought output.

   subject:  A topic label for the reasoning block.

   $$reasoning-event-ext:  A CDDL socket that can be used to extend the
      "reasoning" type Event Object.  See Section 4.1.

4.6.4.  system-event

   A "system-event" type Event Object records system lifecycle events
   that are not part of the conversation dialog but are relevant for
   understanding the session context.  Examples include session start
   and end markers, token usage summaries, permission changes, and
   configuration events.

   event_type:  Classifies the event, such as "session-start", "session-
      end", "token-count", or "permission-change".  The values are not
      enumerated in the schema to accommodate vendor-specific event
      types.

   data:  Event-specific payload.  The structure varies by event type.

   $$system-event-ext:  A CDDL socket that can be used to extend the
      "system-event" type Event Object.  See Section 4.1.

4.7.1.  VCS_Context Object

   The VCS_Context Object captures version control metadata for
   reproducibility.  Knowing the exact repository, branch, and commit at
   the time of a conversation enables consumers to reconstruct the
   codebase state and verify file attributions.  It is used by the vcs
   parameter of the vCon Object (Section 4.2.2) and by the Environment
   Object of the Session Object (Section 4.4.3).

   type:  The version control system type (e.g., "git", "jj", "hg",
      "svn").

   revision:  The commit SHA or change identifier at session time.

   branch:  The active branch name.

   repository:  The repository URL.

4.7.2.  Agent Entry Reference

   Agent implementations identify each entry of their native trace and
   arrange entries in a tree.  The entry_id and parent_id parameters
   preserve this structure in the Dialog Objects (Section 4.5) and the
   Event Objects (Section 4.6) of an agent session.

   entry_id:  A per-entry unique reference within a session, enabling
      parent-child linking.

   parent_id:  References the parent entry, enabling tree-structured
      conversations.  Entries that the native format nests inside
      another entry reference that entry in parent_id.

5.  Compatibility Considerations

   This extension is Compatible as defined in [VCON-CORE].

   The parameters added by this extension to the vCon Object
   (recording_agent, vcs, file_attribution), to the Party Object
   (agent_meta), to the Session Object (agent_session_id, format,
   environment), and to the Dialog Object (model_id, token_usage,
   entry_id, parent_id) are new and optional.  None of them changes the
   meaning, structure, or permitted values of any parameter defined in
   [VCON-CORE].  An implementation that does not recognize these
   parameters can therefore continue to process the vCon correctly by
   ignoring them.

   The Event Object types added by this extension ("tool-call", "tool-
   result", "reasoning", "system-event") are values that an
   implementation that does not support this extension does not
   recognize.  As defined in [VCON-CORE], such an implementation ignores
   these Event Objects, and they remain in the events array so that
   indexes are not changed.  The effect is that the agent trace is not
   processed, while the messages of the agent session, which are Dialog
   Objects, are processed as usual.  This does not make the extension
   Incompatible.

6.  Incompatibility Considerations

   This extension introduces no incompatibilities.  All parameters and
   Event Object types defined in this document are new and additive.
   None of them changes the semantics, structure, or permitted values of
   any parameter defined in [VCON-CORE].  Because no incompatibility is
   introduced, the "ai_agent" extension name is not required to appear
   in the critical parameter.

   A redactor that does not support this extension cannot assess the
   content of the parameters and Event Object types defined in this
   document, which can carry PII (see Section 7).  As described in
   [VCON-CORE], such a redactor may reject a vCon that lists "ai_agent"
   in the extensions parameter.

7.  Privacy and Integrity Considerations

   Verifiable agent conversation records reveal substantial information
   about agent behavior, system state, and user interactions.  The
   privacy considerations of [RFC6973] apply.

7.1.  Information Disclosure

   User prompts captured in Dialog Objects may contain personal
   identifiers, business confidential information, credentials
   inadvertently included in prompts, or behavioral patterns.  Agent
   responses and reasoning traces may reveal inference results that
   expose information about users not explicitly provided, confidential
   information retrieved by tools, or system architecture details
   through tool names and parameters.  Implementations MUST treat user-
   provided content as potentially containing personally identifiable
   information.

   Record metadata exposes operational details that may have privacy
   implications.  Model identifiers reveal AI capabilities, CLI versions
   enable targeted attacks against known vulnerabilities, working
   directories expose file system structure, and VCS context discloses
   repository names and commit timing.  Token usage patterns may enable
   inference about conversation content even when the content itself is
   protected.

7.2.  Sensitive Content in Records

   Reasoning entries may contain inferences that constitute special
   category data, including health-related inferences from user queries,
   political opinions derived from conversation context, or biometric
   data processed by AI systems.  The encrypted parameter of the
   "reasoning" Event Object type reflects that some model providers
   encrypt chain-of-thought content; when reasoning is encrypted, audit
   capabilities depend on the provider's cooperation.

   Tool inputs and outputs warrant particular attention.  Tool call
   inputs may contain credentials, API keys, or file contents.  Tool
   results may contain query results with personal data from databases
   or external services.  Implementations SHOULD provide configurable
   redaction rules for common patterns and support selective entry type
   recording based on deployment requirements.

7.3.  Redaction and De-identification

   The input parameter of "tool-call" type Event Objects, the output
   parameter of "tool-result" type Event Objects, the content and
   encrypted parameters of "reasoning" type Event Objects, and the data
   parameter of "system-event" type Event Objects can carry party-
   identifying data or PII.  The same applies to the Dialog Content of
   the Dialog Objects that represent messages, to the working_dir and
   sandboxes members of the Environment Object, and to the path and url
   members of the File_Attribution Object.  A redactor is expected to
   handle these parameters like Dialog Content, using the redacted
   parameter of [VCON-CORE].  A redactor that removes an Event Object
   entirely leaves a placeholder in the events array, so that indexes in
   other Objects do not change.

7.4.  External References

   This extension does not add url and content_hash parameters for
   externally referenced files as defined in [VCON-CORE], and therefore
   introduces no new externally referenced content.  The url members of
   the File_Conversation Object and of the Resource Object are
   references to related resources and not content of the vCon.  They
   are not protected by a content_hash.

7.5.  Retention Considerations

   Multiple frameworks impose retention requirements that may conflict
   with data minimization principles.  Organizations must balance
   compliance obligations requiring extended retention against privacy
   principles requiring timely deletion.

   Compliant data management may require separating raw personal data
   from audit trail metadata, implementing automated deletion for
   personal data after compliance-minimum periods, and maintaining
   cryptographic commitments enabling verification without retaining
   content.

7.6.  Correlation and Inference

   Presentations of the same record to multiple parties can be
   correlated by matching on the signature component.  Session
   identifiers enable linking of records across time, potentially
   revealing long-term behavioral patterns or organizational structure.
   Implementations SHOULD use unlinkable session identifiers where
   correlation is not required.

   Without accessing record content, observers may infer conversation
   frequency and duration patterns, types of tools used, error rates, or
   timing correlations with external events.  Metadata exposure in
   unprotected headers warrants careful consideration; the trace-
   metadata in the COSE unprotected header (Appendix B) reveals session
   identifiers, agent vendor, and timestamps even when the payload is
   encrypted.

7.7.  Authority Access

   Regulatory frameworks may require provision of records to authorities
   upon request.  Access to records has to be logged, capturing who
   accessed which records, when access occurred, what legal basis
   justified access, and what data was disclosed.  This creates a
   recursive consideration: access logs may themselves contain personal
   data requiring protection.

8.  Security Considerations

   The security considerations of [VCON-CORE] apply.

8.1.  Record Integrity

   The signed form of a vCon [VCON-CORE] and the signed-agent-record
   envelope (Appendix B) provide cryptographic integrity protection for
   the serialized record payload.  A valid signature establishes that
   the claimed signer produced the record but does not guarantee the
   truthfulness of its contents.  Modifications to the record structure
   after signing invalidate the signature, but modifications before
   signing cannot be detected.  Implementations generating records
   incrementally during a conversation MUST sign only after the
   conversation concludes or at defined checkpoints.

8.2.  Signing Key Protection

   The security of signed records depends critically on the protection
   of private signing keys.  If an attacker obtains a signing key, they
   can forge records indistinguishable from genuine ones.  Protection
   mechanisms range from operating system process isolation in
   development environments to hardware security modules with physical
   tampering resistance in high-assurance deployments.  Compromised
   signing keys require rejection of records signed after the compromise
   date and notification to Relying Parties.

   Key provisioning processes must guarantee that exclusively valid
   attestation key material is established.  Off-device key generation
   requires confidentiality protection during transmission, creating
   recursive security dependencies.  On-device key generation eliminates
   transmission risks but requires chain-of-custody integrity to prevent
   attackers from obtaining endorsement for keys they control.

8.3.  Timestamp Integrity

   Timestamps establish temporal ordering of events within records.
   Attackers who can manipulate timestamps can backdate records, freeze
   participants in chosen time periods to evade freshness checks, or
   manipulate perceived temporal relationships between entries.
   Timestamps within records are attested by the signer, not
   independently verified.  Implementations requiring independent
   timestamp verification SHOULD use external timestamping services or
   transparency logs such as those defined in [RFC9943].

8.4.  Adversarial Content

   Processing verifiable agent conversation records involves parsing
   content that may be produced by adversaries.  This applies both to
   user-supplied prompts and to model outputs that may have been
   influenced by adversarial inputs.  The open extensibility (* tstr =>
   any) in the Objects defined in this document allows arbitrary
   additional fields; implementations MUST NOT assume that unrecognized
   fields are safe to process or display.

   Records may contain content designed to exploit downstream systems.
   Malicious prompts preserved in records may execute if records are
   subsequently processed by AI systems.  Tool results may contain
   executable content that executes if rendered unsafely in web
   interfaces.  File paths in tool calls or file attribution entries may
   attempt directory traversal.  Implementations MUST apply appropriate
   sanitization before rendering content, executing it in agent
   contexts, or using paths for file system operations.

8.5.  Non-Repudiation

   The signed form of a vCon and the signed-agent-record envelope alone
   provide authenticity and integrity, not non-repudiation.  A signer
   can claim key compromise or dispute the signing time without
   independent evidence.  Non-repudiation requires additional
   infrastructure such as transparency services [RFC9943] that provide
   independent timestamp proof via registration receipts, append-only
   logs preventing retroactive denial, and third-party witnesses to the
   signing event.

8.6.  Detection and Trust Boundaries

   Verifiable agent conversation records primarily enable detection of
   anomalous behavior rather than prevention.  Detection requires that
   records accurately reflect actual agent behavior; an agent that
   controls its own recording can omit or falsify entries.  The
   recording_agent parameter distinguishes the recording tool from the
   conversing agent, enabling Relying Parties to assess trust in the
   recording process.

   Trust boundaries exist between the agent runtime and recording
   system, between the recording system and storage, between storage and
   verification, and between verification and decision-making.  Attacks
   at any boundary may compromise record integrity or confidentiality.

   +-------------------+-----------------------------------------------+

A.5.  Security Requirements addressing Regulatory Compliance

A.5.1.  Log Integrity

   Per PCI DSS [PCI_DSS_V4_0_1] Req 10.5 and FedRAMP [NIST_SP_800_53_R5]
   AU-9, logs MUST be protected against modification.  Implementations
   SHOULD:

   1.  Use the signed form of the vCon or the signed-agent-record
       envelope (Appendix B) for cryptographic integrity

   2.  Store the content-hash for offline verification

   3.  Implement write-once storage for log archives

A.5.2.  Access Control

   Per FedRAMP [NIST_SP_800_53_R5] AC-3 and ETSI [ETSI_TS_104223_2025]
   5.2.2-1, access to logs MUST be controlled:

   1.  Logs containing sensitive prompts or outputs require access
       control

   2.  Reasoning content may contain confidential information

   3.  Authority access (EU AI Act Art. 19) requires audit of log access
       itself

A.5.3.  Data Protection

   Logs may contain personal data subject to GDPR/privacy regulations:

   1.  Dialog Content of text Dialog Objects may contain PII

   2.  output of tool-result Event Objects may contain query results
       with PII

   3.  Retention periods must balance compliance requirements with data
       minimization

A.6.  Related Standards and Emerging Work

   The ISO/IEC JTC 1/SC 42 committee is developing [ISO_IEC_DIS_24970],
   a draft international standard specifically addressing AI system
   logging requirements.  This work aligns with and complements the
   verifiable agent conversation format defined in this document.

   Research on emergent misalignment [EMERGENT_MISALIGNMENT_2025]
   demonstrates that narrow fine-tuning can produce broadly misaligned
   LLMs, underscoring the importance of comprehensive conversation
   logging for detecting behavioral anomalies that may not be apparent
   from individual interactions.

Appendix B.  Application of SCITT and COSE for Transparency and
             Authenticity

   The signed form of a vCon [VCON-CORE] uses JWS.  This appendix
   describes a signing envelope that provides cryptographic integrity
   protection for vCons that carry agent conversation records using
   COSE_Sign1 ([STD96]), which is encoded in CBOR [STD94].  The vCon is
   the payload of the envelope, and the content type header parameter
   carries the media type "application/vcon" defined in [VCON-CORE].
   This makes a signed agent record a Signed Statement that can be
   registered with a SCITT Transparency Service [RFC9943].  No extension
   point of the vCon schema is used by the envelope.  The reader is
   assumed to be familiar with the vocabulary and concepts defined in
   [RFC9334] and [RFC9943].

   Editor's Note:  The use of COSE and SCITT for vCons is expected to
      progress together with the SCITT related vCon work.

   The collated CDDL definition for the envelope is specified as
   follows:

   =============== NOTE: '\' line wrapping per RFC 8792 ================

   signed-agent-record = #6.18([           ; COSE_Sign1 tag
       protected: bstr .cbor protected-header ; {alg, content-type, \
                                                            scitt-stuff}
       unprotected: unprotected-header     ; Trace metadata
       payload: bstr / null                ; Detached if null
       signature: bstr
   ])

   protected-header = {
     &(CWT_Claims: 15) => CWT_Claims
     ? &(alg: 1) => int
     ? &(content_type: 3) => tstr / uint
     ? &(kid: 4) => bstr
     ? &(x5t: 34) => COSE_CertHash
     ? &(x5chain: 33) => COSE_X509
     * label => any
   }

   CWT_Claims = {
     &(iss: 1) => tstr
     &(sub: 2) => tstr
     * label => any
   }

   unprotected-header = {
     ? &(trace-metadata-key: 100) => trace-metadata ; 100 is placeholder
     ? &(x5chain: 33) => COSE_X509
     ? &(receipts: 394)  => [ + Receipt ]
     * label => any
   }

   trace-metadata = {
       session-id: session-id
       agent-vendor: tstr
       trace-format: trace-format-id
       timestamp-start: abstract-timestamp
       ? timestamp-end: abstract-timestamp
       ? content-hash: tstr                ; SHA-256 hex digest of \
                                                                 payload
       ? content-hash-alg: tstr
   }

   ; Known values: "ietf-vac-v3.0" (canonical), "claude-jsonl", "gemini\
                                                                 -json",
   ; "codex-jsonl", "opencode-json", "cursor-jsonl". Extensible via \
                                                                   tstr.
   trace-format-id = tstr

   COSE_X509 = bstr / [ 2*certs: bstr ]
   COSE_CertHash = [ hashAlg: (int / tstr), hashValue: bstr ]
   label = int / tstr

   ; COSE Receipt CDDL for use in SCITT compliant COSE Envelope

   Receipt = #6.18(COSE_Sign1)

   cose-label = int / tstr
   cose-value = any

   Protected_Header = {
     * cose-label => cose-value
   }

   Unprotected_Header = {
     &(receipts: 394)  => [+ bstr .cbor Receipt]
     * cose-label => cose-value
   }

   COSE_Sign1 = [
     protected   : bstr .cbor Protected_Header,
     unprotected : Unprotected_Header,
     payload     : bstr / null,
     signature   : bstr
   ]



   ; SCITT-interoperable COSE Envelope
   ; including from draft-ietf-cose-merkle-tree-proofs and
   ; draft-ietf-scitt-architecture for validation

   ; RFC 3339 string OR epoch milliseconds (for interop).
   abstract-timestamp = tstr .regexp date-time-regexp / uint

   ; Opaque string: UUID, SHA-256 hash in base64url, etc.
   session-id = tstr / bstr

   ; RFC 3339 date-time pattern
   date-time-regexp = "([0-9]{4})-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[\
   01])T([01][0-9]|2[0-3]):([0-5][0-9]):(60|[0-5][0-9])([.][0-9]+)?(Z|[\
                                      +-]([01][0-9]|2[0-3]):[0-5][0-9])"

B.1.  The signed-agent-record Structure

   A signed-agent-record is a COSE_Sign1 envelope (CBOR Tag 18) that
   wraps a vCon with a cryptographic signature.  Signing provides data
   provenance and tamper evidence, satisfying some requirements of RATS
   Evidence generation ([RFC9334]) and SCITT auditability ([RFC9943])
   requirements.  The payload may be included or detached (null); in
   detached mode, the vCon is supplied separately during verification.

   The following describes each element of this structure.

   protected:  The serialized protected header containing the algorithm
      identifier, content type, and CWT claims [RFC9597].

   unprotected:  The unprotected header carrying trace metadata at label
      100 and, after registration, the receipts [RFC9942] of a SCITT
      Transparency Service.

   payload:  The serialized vCon bytes, or null for detached payloads.

   signature:  The cryptographic signature over the protected header and
      payload.

   The x5chain and x5t header parameters are defined in [RFC9360].

B.2.  The trace-metadata Map

   The trace-metadata type carries summary information about the signed
   record in the COSE_Sign1 unprotected header.  This enables consumers
   to inspect key properties of a signed record without deserializing
   the full payload.

   The following describes each member of this map.

   session-id:  The session identifier from the signed record.

   agent-vendor:  The agent provider name (e.g., "anthropic", "google").

   trace-format:  Identifies the format of the signed payload (e.g.,
      "ietf-vac-v3.0" for canonical records).

   timestamp-start:  When the session began.

   timestamp-end:  When the session ended.

   content-hash:  SHA-256 hex digest of the payload bytes, enabling
      integrity checking independent of the COSE signature.

   content-hash-alg:  The hash algorithm used (default: "sha-256").

   Editor's Note:  The label 100 for trace-metadata is a placeholder.  A
      COSE Header Parameter registration is for further discussion.

Appendix E.  CDDL for the ai_agent Extension

   This appendix provides a [CDDL] definition for the parameters defined
   by the ai_agent extension.  The text in the preceding sections of
   this document defines the normative definition of these parameters.
   If the CDDL provided below differs from that in the text of the
   preceding sections, the text is the definitive definition and the
   CDDL below is to be considered incorrect.

   This CDDL extends the vcon-ext, party-ext, session-ext, dialog-ext,
   and event-type-ext sockets of the vCon CDDL of [VCON-CORE].  It is to
   be used together with the vCon CDDL, which comes first so that its
   first rule is the root of the combined definition.  The fragments
   below are the same ones that are included in the preceding sections,
   in the order in which they are included by the main CDDL file of this
   extension, which starts with the root rule "vcon-with-ai-agent =
   vcon" and includes the vCon CDDL first.

   $$vcon-ext //= ( recording_agent: recording_agent_type )
   $$vcon-ext //= ( vcs: vcs_context_type )
   $$vcon-ext //= ( file_attribution: file_attribution_type )

   ; Recording_Agent Object
   recording_agent_type = {
       name: tstr,
       ? version: tstr,
       * tstr => any
     }

   ; File_Attribution Object
   file_attribution_type = {
       files: [* file_type],
       * $$file-attribution-ext
     }

   ; File Object
   file_type = {
       ; relative path from the repository root
       path: tstr,
       conversations: [* file_conversation_type],
       * $$file-ext
     }

   ; File_Conversation Object
   file_conversation_type = {
       ? url: uri_type,
       ; default contributor for all ranges
       ? contributor: contributor_type,
       ranges: [* range_type],
       ? related: [* resource_type],
       * $$file-conversation-ext
     }

   ; Range Object
   range_type = {
       ; 1-indexed
       start_line: uint,
       ; 1-indexed, inclusive
       end_line: uint,
       ? content_hash: tstr,
       ; default: "sha-256"
       ? content_hash_alg: tstr,
       ; overrides the conversation level contributor
       ? contributor: contributor_type,
       * $$range-ext
     }

   ; Contributor Object
   contributor_type = {
       type: "human" / "ai" / "mixed" / "unknown",
       ? model_id: tstr,
       * $$contributor-ext
     }

   ; Resource Object
   resource_type = {
       type: tstr,
       url: uri_type,
       * $$resource-ext
     }

   ; URI (RFC 3986)
   uri_type = tstr .regexp
       "(([^:/?#]+):)?(//([^/?#]*))?([^?#]*)(\\?([^#]*))?(#(.*))?"

   $$party-ext //= ( agent_meta: agent_meta_type )

   ; Agent_Meta Object
   agent_meta_type = {
       ; e.g., "claude-opus-4-5-20251101"
       model_id: tstr,
       ; e.g., "anthropic", "google"
       model_provider: tstr,
       ; all models (multi-model sessions)
       ? models: [* tstr],
       ; e.g., "claude-code", "gemini-cli"
       ? cli_name: tstr,
       ? cli_version: tstr,
       * tstr => any
     }

   $$session-ext //= ( agent_session_id: tstr )
   ; "interactive" / "autonomous" / vendor specific
   $$session-ext //= ( format: tstr )
   $$session-ext //= ( environment: environment_type )

   ; Environment Object
   environment_type = {
       working_dir: tstr,
       ? vcs: vcs_context_type,
       ; sandbox mount paths
       ? sandboxes: [* tstr],
       * tstr => any
     }

   $$dialog-ext //= ( model_id: tstr )
   $$dialog-ext //= ( token_usage: token_usage_type )
   $$dialog-ext //= ( entry_id: agent_entry_id_type )
   $$dialog-ext //= ( parent_id: agent_entry_id_type )

   ; Token_Usage Object
   token_usage_type = {
       ; input tokens
       ? input: uint,
       ; output tokens
       ? output: uint,
       ; cached input tokens
       ? cached: uint,
       ; reasoning or thinking tokens
       ? reasoning: uint,
       ; total tokens
       ? total: uint,
       ; monetary cost in US dollars
       ? cost: number,
       * tstr => any
     }

   $$event-type-ext //= (event_tool_call_type,)
   $$event-type-ext //= (event_tool_result_type,)
   $$event-type-ext //= (event_reasoning_type,)
   $$event-type-ext //= (event_system_event_type,)

   ; "tool-call" type Event Object
   event_tool_call_type = (
       type: "tool-call",
       event_common_type,
       ; e.g., "Bash", "Edit", "Read"
       tool_name: tstr,
       ; tool arguments
       input: any,
       ; links call and result
       ? call_id: tstr,
       agent_entry_reference_type,
       * $$tool-call-event-ext
     )

   ; "tool-result" type Event Object
   event_tool_result_type = (
       type: "tool-result",
       event_common_type,
       ; tool output
       output: any,
       ; links call and result
       ? call_id: tstr,
       ; "success" / "error" / "completed"
       ? status: tstr,
       ? is_error: bool,
       agent_entry_reference_type,
       * $$tool-result-event-ext
     )

   ; "reasoning" type Event Object
   event_reasoning_type = (
       type: "reasoning",
       event_common_type,
       ; plaintext reasoning or structured content
       content: any,
       ; provider protected content
       ? encrypted: tstr,
       ; topic label
       ? subject: tstr,
       agent_entry_reference_type,
       * $$reasoning-event-ext
     )

   ; "system-event" type Event Object
   event_system_event_type = (
       type: "system-event",
       event_common_type,
       ; event classifier
       event_type: tstr,
       ; event specific payload
       ? data: { * tstr => any },
       agent_entry_reference_type,
       * $$system-event-ext
     )

   vcs_context_type = {
       ; "git" / "jj" / "hg" / "svn"
       type: tstr,
       ; commit SHA or change ID
       ? revision: tstr,
       ? branch: tstr,
       ; repository URL
       ? repository: tstr,
       * tstr => any
     }

   ; Reference to an entry of the native agent trace
   agent_entry_reference_type = (
       ? entry_id: agent_entry_id_type,
       ? parent_id: agent_entry_id_type
     )

   ; Per-entry unique reference within a session
   agent_entry_id_type = tstr
