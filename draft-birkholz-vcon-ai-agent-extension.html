An AI Agent Extension for Virtualized Conversations (vCon)

Abstract

A vCon is a container for data and information relating to a conversation. This document defines an extension to the vCon core specification via the CDDL extension points provided. The ai agent vCon extension specified in this document is in support of verifiable records of conversations with and between autonomous agents. Autonomous agents that use large language models increasingly perform consequential tasks on behalf of humans and other agents. Demonstrating that recorded agent behavior truthfully represents actual behavior is essential for accountability, compliance, and human oversight. The vCon extension specified in this document captures agent trajectory and agent conversation related records, such as agent metadata, message exchanges, tool invocations, reasoning traces, system events, file attribution, etc. This data and information about autonomous agent behaviour are recorded as parameters of vCon Objects and as new vCon Event Object types. The data CDDL definitions originate from the former Verifiable Agent Conversation Records specification and are adapted to the extension points of the current vCon CDDL data defintition.¶

1. Introduction

This document adds parameters and Event Object types for autonomous agents to the vCon CDDL definition as described in [VCON-CORE]. The general framework and requirements for defining an extension to vCon CDDL definition are defined in [VCON-CORE].¶

The question of whether the recorded output of an autonomous agent faithfully represents an agent's actual behavior has found new urgency as the number of consequential tasks that are delegated to agents increases rapidly. Autonomous Agents--typically workload instances of agentic artificial intelligence (AI) based on large language models (LLM)--interact with other actors by design. This creates an interconnected web of agent interactions and conversations that is currently rarely supervised or recorded in a systemic manner. In essence, the two main types of actors interacting with autonomous agents are humans and machines (e.g., other autonomous agents), or a mix of them. In agentic AI systems, machine actors interact with other machine actors. The number of interactions between machine actors grows significantly more than the number of interactions between human actors and machine actors. While the responsible parties for agent actions ultimately are humans--whether a natural legal entity or an organization--agents act on behalf of humans and on behalf of other agents. To demonstrate due diligence, responsible human parties require records of agent behavior to demonstrate policy compliant behavior for agents acting under their authority. These increasingly complex interactions between multiple actors that can also be triggered by machines (recursively) increase the need to understand decision making and the chain of thoughts (CoT) of autonomous agents, retroactively (i.e., accountability and auditability after the fact).¶

The verifiable records of agent conversations that are specified in this document provide an essential basis for operators to detect divergences between intended and actual agent behavior after the interaction has concluded.¶

For example:¶

  • An agent authorized to read files might invoke tools to modify production systems or exfiltrate sensitive data beyond its authorization scope.¶

  • An agent's visible CoT output might diverge from the reasoning that actually produced its actions.¶

  • An agent might deliberately underperform during capability evaluations while performing at full capacity during deployment.¶

This document defines conversation records extensions for vCon representing activities of autonomous agents such that long-term preservation of the evidentiary value of such records across chains of custody (CoC) is possible.¶

This document defines vCon extensions that integrate verifiable records of agent conversations as a building block into vCon towards seven dedicated goals:¶

  1. The first goal is to assure that the recording of an agent conversation (a distinct segment of the interaction with an autonomous agent) being proffered is the same as the agent conversation that actually occurred.¶

  2. The second goal is to provide a general structure of agent conversations that can represent most common types of agent conversation frames, is extensible, and allows for future evolution of agent conversation complexity and corresponding actor interaction.¶

  3. The third goal is to use existing IETF building blocks to present believable evidence about how an agent conversation is recorded utilizing Evidence generation as laid out in the Remote ATtestation ProcedureS architecture [RFC9334].¶

  4. The fourth goal is to use existing IETF building blocks to render conversation records auditable after the fact and enable non-repudiation as laid out in the Supply Chain Integrity, Transparency, and Trust architecture [RFC9943].¶

  5. The fifth goal is to enable detection of behavioral anomalies in agent interactions, including unauthorized tool invocations, inconsistencies between reasoning traces and actions, and performance modulation across evaluation and deployment contexts, through structured, comparable conversation records.¶

  6. The sixth goal is to enable cross-vendor interoperability by defining a common representation for agent conversations that can be translated from multiple existing agent implementations with distinct native formats.¶

  7. The seventh goal is to produce records suitable for demonstrating compliance with emerging regulatory requirements for AI system documentation, traceability, and human oversight.¶

Most agent conversations today are represented in "human-readable" text formats. For example, JSON [JSON] is considered to be "human-readable" as it can be presented to humans in human-computer-interfaces (HCI) via off-the-shelf tools, e.g., pre-installed text editors that allow such data to be consumed or modified by humans. A vCon is a JSON document, and so are the agent conversation records extensions defined in this document. The signed and the encrypted forms of a vCon defined in [VCON-CORE] apply unchanged. The application of COSE [STD96] to vCons that carry agent conversation vCon records is described in the SCITT architecture Appendix B.¶

1.1. Transition from Verifiable Agent Conversation Records to a vCon extension

The data definitions in this document originate from the stand-alone Verifiable Agent Conversation Records specification [VACR]. This Internet-Draft rebuilds them as an extension of the vCon CDDL definition. Each high level part of a Verifiable Agent Conversation Record is assigned to one of the extension points that [VCON-CORE] defines as CDDL [CDDL] sockets, and the sections of this document follow these extension points. CDDL definitions that are used by more than one extension point are collected in Section 4.7 after the sections for the extension points. Appendix C maps each data item of [VACR] to its place in this document.¶

The vCon concepts of Session and Event that this extension builds upon were proposed to accommodate AI agent conversations in [ROSENBERG-RESTRUCTURE]. [HOWE-AGENT-SESSION] and [HOWE-PROVENANCE] describe related approaches that carry agent session data and generation provenance in a vCon.¶

The assignment of each part of a Verifiable Agent Conversation Record to a vCon extension point is preliminary. Each section that defines parameters for an extension point lists alternatives that are still open for discussion.¶

2.1. Terminology

See the Terminology section of [VCON-CORE] for terminology used in this document.¶

The following terms are used in this document:¶

Agent:

An autonomous software system, typically based on a large language model, that is represented by a Party Object and that produces messages, invokes tools, and produces reasoning.¶

Agent Session:

A session of an agent, represented by a Session Object.¶

Entry:

A discrete, system-recorded event of an agent session in the native format of an agent implementation, such as a message, a tool call, a tool result, a reasoning step, or a system event. In a vCon, an entry is represented by a Dialog Object or by an Event Object.¶

Recording Agent:

The tool or agent that generates the vCon, as distinct from the agent that conducted the conversation.¶

3. Extension Name

The extension name for this document is "ai_agent".¶

The string token "ai_agent" SHOULD be included in the extensions parameter of a vCon that contains any of the parameters or Event Object types defined in this document. As described in Section 5 and Section 6, this extension is intended to be fully interoperable with the vCon definitions and the name "ai_agent" is not inlcuded as a critical parameter.¶

4. Parameter Definitions

This section defines the parameters and Event Object types of the "ai_agent" extension. There is one subsection for each extension point of [VCON-CORE] that this extension uses. Each subsection contains the CDDL that plugs into the corresponding socket of the vCon CDDL. New Objects are defined in the subsection of the extension point at which they are introduced.¶

The Verifiable Agent Conversation Record of [VACR] is a top-level container for all data produced by or about an agent conversation. In this extension, the vCon Object is that container. The uuid parameter of the vCon Object identifies the record, and the created_at parameter of the vCon Object provides the time the record was generated. The extension name in the extensions parameter replaces the schema version string, as the extension mechanism of [VCON-CORE] replaces schema versioning. The record unifies two complementary perspectives: the agent session captures how code was produced (the full conversation replay), while file attribution captures what code was produced (which files were modified and by whom).¶

This extension adds the following parameter to the Party Object, using the party-ext socket:¶

4.3.1. agent_meta

The agent_meta parameter identifies the coding agent and language model that a Party Object represents. Agent identification is essential for provenance tracking: knowing which model produced which output enables auditing, capability assessment, and compliance verification. The type parameter of a Party Object that contains agent_meta SHOULD be "bot".¶

The Agent_Meta Object contains the following members:¶

The primary language model identifier, using the naming convention of the provider (e.g., "claude-opus-4-5-20251101", "gemini-2.0-flash").¶

List of all model identifiers used during the session. Relevant for multi-model sessions where the agent switches between models.¶

The name of the CLI tool or agent framework (e.g., "claude-code", "gemini-cli", "codex-cli").¶

cli_version:

The version of the CLI tool.¶

4.4. Session Object Parameters

An agent session is represented by a Session Object. It captures the full conversation between a user and an autonomous agent. The Dialog Objects and Event Objects that are part of the Session Object represent messages, tool invocations, reasoning steps, and system events. Together, they preserve the complete interaction history including all native agent metadata, enabling both replay and audit of the conversation. The start parameter of the Session Object provides the time the agent session began, and the duration parameter provides the time until the agent session ended. An agent that spawns sub-agents is represented by a Session Object that references the Session Objects of the sub-agents using the Session_Reference type "child", as described for AI agents in [VCON-CORE].¶

This extension adds the following parameters to the Session Object, using the session-ext socket:¶

4.4.1. agent_session_id

The agent_session_id parameter contains an opaque string uniquely identifying the agent session in the native format of the agent implementation. Values may be UUID v4, UUID v7, SHA-256 hashes, or other formats. The agent_session_id parameter is distinct from the session_id parameter of the Session Object, which contains a SessionId Object.¶

  • agent_session_id: "String" (optional)¶

4.4.2. format

The format parameter classifies the session style, such as "interactive" (human-in-the-loop) or "autonomous" (fully automated). Informative only; does not change the structure.¶

  • format: "String" (optional)¶

4.4.3. environment

The environment parameter captures execution context for the conversation: where the agent was running, what version control state was active, and whether sandboxing was in effect. This context is important for reproducibility and for understanding the scope of file modifications.¶

  • environment: "Environment" (optional)¶

The Environment Object contains the following members:¶

working_dir:

The primary working directory path. File paths in tool calls are typically relative to this directory.¶

vcs:

Version control state at the time of the session (branch, revision, etc.), as a VCS_Context Object (Section 4.7.1).¶

sandboxes:

Paths to sandbox mount points. Some agents run in sandboxed environments where the working directory is a temporary mount.¶

4.5. Dialog Object Parameters

A message of an agent session represents a conversational turn: either human input or agent response. This is the most common entry type, carrying the primary dialog content of a session. A message is represented by a "text" type Dialog Object. The parties parameter of the Dialog Object references the Party Object of the contributor of the message. Human (or upstream agent) input is contributed by the Party Object of the user, and an agent response is contributed by the Party Object of the agent. The message body is contained in the Dialog Content. For assistant messages, additional metadata may be present: the model that generated the response and token usage statistics.¶

This extension adds the following parameters to the Dialog Object, using the dialog-ext socket:¶

Editor's Note:

An alternative placement for model_id and token_usage is the generation provenance of [HOWE-PROVENANCE].¶

4.5.1. model_id

The model_id parameter identifies the model that generated this response. Present on assistant messages, absent on user messages.¶

  • model_id: "String" (optional)¶

4.5.2. token_usage

The token_usage parameter captures token consumption metrics for a model response. Token usage data is essential for cost tracking, quota management, and understanding model behavior. All members are optional because different agents report different subsets of token metrics.¶

  • token_usage: "Token_Usage" (optional)¶

The entry_id parameter contains the unique identifier of this entry within the session. The parent_id parameter references the parent entry, enabling tree-structured conversations. Both are defined in Section 4.7.2.¶

4.6. Event Object Types and Parameters

This extension defines four Event Object types representing the kinds of entries in an agent conversation that are not messages. They are added using the event-type-ext socket. Each type ends with a socket of its own, so that other extensions can add parameters to it.¶

For all four types, the time parameter provides when the entry occurred, the session parameter references the Session Object of the agent session, and the party parameter references the Party Object of the agent. The entry_id and parent_id parameters (Section 4.7.2) preserve the native entry identifiers and the tree structure of the agent trace.¶

Editor's Note:

An alternative placement for the agent trace is a single Analysis Object that carries the trace, as proposed in [HOWE-AGENT-SESSION]. It is also an open question whether the "tool-call" and "reasoning" Event Object types apply to human parties.¶

4.6.1. tool-call

A "tool-call" type Event Object represents a tool invocation: which tool was called and with what arguments. Tool calls are central to agent conversation records because tool use is the primary mechanism by which agents interact with external environment.¶

tool_name:

The tool name (e.g., "Bash", "Edit", "Read", "apply_patch").¶

input:

The arguments passed to the tool, preserved in their native structure.¶

call_id:

Links this call to its corresponding result.¶

$$tool-call-event-ext:

A CDDL socket that can be used to extend the "tool-call" type Event Object. See Section 4.1.¶

4.6.2. tool-result

A "tool-result" type Event Object represents the output returned by a tool after execution. It is linked to its corresponding "tool-call" type Event Object via the call_id parameter. The result carries the tool's response data and optional status metadata indicating success or failure.¶

output:

The tool's response, preserved in native structure.¶

call_id:

Links this result to its corresponding call.¶

status:

Outcome status of the tool execution, such as "success", "error", or "completed".¶

is_error:

Boolean error flag, present when the tool execution failed.¶

$$tool-result-event-ext:

A CDDL socket that can be used to extend the "tool-result" type Event Object. See Section 4.1.¶

4.6.3. reasoning

A "reasoning" type Event Object captures CoT, thinking, or internal reasoning content from the agent. Not all agents expose reasoning traces. When they do, the content may be plaintext, structured blocks, or encrypted. Reasoning entries are valuable for auditing decision-making processes and understanding why an agent took particular actions.¶

content:

The reasoning text or structured content. May be an empty string when only encrypted content is available.¶

encrypted:

Encrypted reasoning content. Used where the model provider encrypts chain-of-thought output.¶

subject:

A topic label for the reasoning block.¶

$$reasoning-event-ext:

5. Compatibility Considerations

This extension is Compatible as defined in [VCON-CORE].¶

The parameters added by this extension to the vCon Object (recording_agent, vcs, file_attribution), to the Party Object (agent_meta), to the Session Object (agent_session_id, format, environment), and to the Dialog Object (model_id, token_usage, entry_id, parent_id) are new and optional. None of them changes the meaning, structure, or permitted values of any parameter defined in [VCON-CORE]. An implementation that does not recognize these parameters can therefore continue to process the vCon correctly by ignoring them.¶

The Event Object types added by this extension ("tool-call", "tool-result", "reasoning", "system-event") are values that an implementation that does not support this extension does not recognize. As defined in [VCON-CORE], such an implementation ignores these Event Objects, and they remain in the events array so that indexes are not changed. The effect is that the agent trace is not processed, while the messages of the agent session, which are Dialog Objects, are processed as usual. This does not make the extension Incompatible.¶

6. Incompatibility Considerations

This extension introduces no incompatibilities. All parameters and Event Object types defined in this document are new and additive. None of them changes the semantics, structure, or permitted values of any parameter defined in [VCON-CORE]. Because no incompatibility is introduced, the "ai_agent" extension name is not required to appear in the critical parameter.¶

A redactor that does not support this extension cannot assess the content of the parameters and Event Object types defined in this document, which can carry PII (see Section 7). As described in [VCON-CORE], such a redactor may reject a vCon that lists "ai_agent" in the extensions parameter.¶

7. Privacy and Integrity Considerations

Verifiable agent conversation records reveal substantial information about agent behavior, system state, and user interactions. The privacy considerations of [RFC6973] apply.¶

7.1. Information Disclosure

User prompts captured in Dialog Objects may contain personal identifiers, business confidential information, credentials inadvertently included in prompts, or behavioral patterns. Agent responses and reasoning traces may reveal inference results that expose information about users not explicitly provided, confidential information retrieved by tools, or system architecture details through tool names and parameters. Implementations MUST treat user-provided content as potentially containing personally identifiable information.¶

Record metadata exposes operational details that may have privacy implications. Model identifiers reveal AI capabilities, CLI versions enable targeted attacks against known vulnerabilities, working directories expose file system structure, and VCS context discloses repository names and commit timing. Token usage patterns may enable inference about conversation content even when the content itself is protected.¶

7.2. Sensitive Content in Records

Reasoning entries may contain inferences that constitute special category data, including health-related inferences from user queries, political opinions derived from conversation context, or biometric data processed by AI systems. The encrypted parameter of the "reasoning" Event Object type reflects that some model providers encrypt chain-of-thought content; when reasoning is encrypted, audit capabilities depend on the provider's cooperation.¶

Tool inputs and outputs warrant particular attention. Tool call inputs may contain credentials, API keys, or file contents. Tool results may contain query results with personal data from databases or external services. Implementations SHOULD provide configurable redaction rules for common patterns and support selective entry type recording based on deployment requirements.¶

7.3. Redaction and De-identification

The input parameter of "tool-call" type Event Objects, the output parameter of "tool-result" type Event Objects, the content and encrypted parameters of "reasoning" type Event Objects, and the data parameter of "system-event" type Event Objects can carry party-identifying data or PII. The same applies to the Dialog Content of the Dialog Objects that represent messages, to the working_dir and sandboxes members of the Environment Object, and to the path and url members of the File_Attribution Object. A redactor is expected to handle these parameters like Dialog Content, using the redacted parameter of [VCON-CORE]. A redactor that removes an Event Object entirely leaves a placeholder in the events array, so that indexes in other Objects do not change.¶

7.4. External References

This extension does not add url and content_hash parameters for externally referenced files as defined in [VCON-CORE], and therefore introduces no new externally referenced content. The url members of the File_Conversation Object and of the Resource Object are references to related resources and not content of the vCon. They are not protected by a content_hash.¶

7.5. Retention Considerations

Multiple frameworks impose retention requirements that may conflict with data minimization principles. Organizations must balance compliance obligations requiring extended retention against privacy principles requiring timely deletion.¶

Compliant data management may require separating raw personal data from audit trail metadata, implementing automated deletion for personal data after compliance-minimum periods, and maintaining cryptographic commitments enabling verification without retaining content.¶

7.6. Correlation and Inference

Presentations of the same record to multiple parties can be correlated by matching on the signature component. Session identifiers enable linking of records across time, potentially revealing long-term behavioral patterns or organizational structure. Implementations SHOULD use unlinkable session identifiers where correlation is not required.¶

Without accessing record content, observers may infer conversation frequency and duration patterns, types of tools used, error rates, or timing correlations with external events. Metadata exposure in unprotected headers warrants careful consideration; the trace-metadata in the COSE unprotected header (Appendix B) reveals session identifiers, agent vendor, and timestamps even when the payload is encrypted.¶

7.7. Authority Access

Regulatory frameworks may require provision of records to authorities upon request. Access to records has to be logged, capturing who accessed which records, when access occurred, what legal basis justified access, and what data was disclosed. This creates a recursive consideration: access logs may themselves contain personal data requiring protection.¶

8. Security Considerations

The security considerations of [VCON-CORE] apply.¶

8.1. Record Integrity

The signed form of a vCon [VCON-CORE] and the signed-agent-record envelope (Appendix B) provide cryptographic integrity protection for the serialized record payload. A valid signature establishes that the claimed signer produced the record but does not guarantee the truthfulness of its contents. Modifications to the record structure after signing invalidate the signature, but modifications before signing cannot be detected. Implementations generating records incrementally during a conversation MUST sign only after the conversation concludes or at defined checkpoints.¶

8.2. Signing Key Protection

The security of signed records depends critically on the protection of private signing keys. If an attacker obtains a signing key, they can forge records indistinguishable from genuine ones. Protection mechanisms range from operating system process isolation in development environments to hardware security modules with physical tampering resistance in high-assurance deployments. Compromised signing keys require rejection of records signed after the compromise date and notification to Relying Parties.¶

Key provisioning processes must guarantee that exclusively valid attestation key material is established. Off-device key generation requires confidentiality protection during transmission, creating recursive security dependencies. On-device key generation eliminates transmission risks but requires chain-of-custody integrity to prevent attackers from obtaining endorsement for keys they control.¶

8.3. Timestamp Integrity

Timestamps establish temporal ordering of events within records. Attackers who can manipulate timestamps can backdate records, freeze participants in chosen time periods to evade freshness checks, or manipulate perceived temporal relationships between entries. Timestamps within records are attested by the signer, not independently verified. Implementations requiring independent timestamp verification SHOULD use external timestamping services or transparency logs such as those defined in [RFC9943].¶

8.4. Adversarial Content

Processing verifiable agent conversation records involves parsing content that may be produced by adversaries. This applies both to user-supplied prompts and to model outputs that may have been influenced by adversarial inputs. The open extensibility (* tstr => any) in the Objects defined in this document allows arbitrary additional fields; implementations MUST NOT assume that unrecognized fields are safe to process or display.¶

Records may contain content designed to exploit downstream systems. Malicious prompts preserved in records may execute if records are subsequently processed by AI systems. Tool results may contain executable content that executes if rendered unsafely in web interfaces. File paths in tool calls or file attribution entries may attempt directory traversal. Implementations MUST apply appropriate sanitization before rendering content, executing it in agent contexts, or using paths for file system operations.¶

8.5. Non-Repudiation

The signed form of a vCon and the signed-agent-record envelope alone provide authenticity and integrity, not non-repudiation. A signer can claim key compromise or dispute the signing time without independent evidence. Non-repudiation requires additional infrastructure such as transparency services [RFC9943] that provide independent timestamp proof via registration receipts, append-only logs preventing retroactive denial, and third-party witnesses to the signing event.¶

8.6. Detection and Trust Boundaries

Verifiable agent conversation records primarily enable detection of anomalous behavior rather than prevention. Detection requires that records accurately reflect actual agent behavior; an agent that controls its own recording can omit or falsify entries. The recording_agent parameter distinguishes the recording tool from the conversing agent, enabling Relying Parties to assess trust in the recording process.¶

Trust boundaries exist between the agent runtime and recording system, between the recording system and storage, between storage and verification, and between verification and decision-making. Attacks at any boundary may compromise record integrity or confidentiality.¶

A.5. Security Requirements addressing Regulatory Compliance

A.5.1. Log Integrity

Per PCI DSS [PCI_DSS_V4_0_1] Req 10.5 and FedRAMP [NIST_SP_800_53_R5] AU-9, logs MUST be protected against modification. Implementations SHOULD:¶

  1. Use the signed form of the vCon or the signed-agent-record envelope (Appendix B) for cryptographic integrity¶

  2. Store the content-hash for offline verification¶

  3. Implement write-once storage for log archives¶

A.5.2. Access Control

Per FedRAMP [NIST_SP_800_53_R5] AC-3 and ETSI [ETSI_TS_104223_2025] 5.2.2-1, access to logs MUST be controlled:¶

  1. Logs containing sensitive prompts or outputs require access control¶

  2. Reasoning content may contain confidential information¶

  3. Authority access (EU AI Act Art. 19) requires audit of log access itself¶

A.5.3. Data Protection

Logs may contain personal data subject to GDPR/privacy regulations:¶

  1. Dialog Content of text Dialog Objects may contain PII¶

  2. output of tool-result Event Objects may contain query results with PII¶

  3. Retention periods must balance compliance requirements with data minimization¶

A.6. Related Standards and Emerging Work

The ISO/IEC JTC 1/SC 42 committee is developing [ISO_IEC_DIS_24970], a draft international standard specifically addressing AI system logging requirements. This work aligns with and complements the verifiable agent conversation format defined in this document.¶

Research on emergent misalignment [EMERGENT_MISALIGNMENT_2025] demonstrates that narrow fine-tuning can produce broadly misaligned LLMs, underscoring the importance of comprehensive conversation logging for detecting behavioral anomalies that may not be apparent from individual interactions.¶

Appendix B. Application of SCITT and COSE for Transparency and Authenticity

The signed form of a vCon [VCON-CORE] uses JWS. This appendix describes a signing envelope that provides cryptographic integrity protection for vCons that carry agent conversation records using COSE_Sign1 ([STD96]), which is encoded in CBOR [STD94]. The vCon is the payload of the envelope, and the content type header parameter carries the media type "application/vcon" defined in [VCON-CORE]. This makes a signed agent record a Signed Statement that can be registered with a SCITT Transparency Service [RFC9943]. No extension point of the vCon schema is used by the envelope. The reader is assumed to be familiar with the vocabulary and concepts defined in [RFC9334] and [RFC9943].¶

Editor's Note:

The use of COSE and SCITT for vCons is expected to progress together with the SCITT related vCon work.¶

The collated CDDL definition for the envelope is specified as follows:¶

B.1. The signed-agent-record Structure

A signed-agent-record is a COSE_Sign1 envelope (CBOR Tag 18) that wraps a vCon with a cryptographic signature. Signing provides data provenance and tamper evidence, satisfying some requirements of RATS Evidence generation ([RFC9334]) and SCITT auditability ([RFC9943]) requirements. The payload may be included or detached (null); in detached mode, the vCon is supplied separately during verification.¶

The following describes each element of this structure.¶

protected:

The serialized protected header containing the algorithm identifier, content type, and CWT claims [RFC9597].¶

unprotected:

The unprotected header carrying trace metadata at label 100 and, after registration, the receipts [RFC9942] of a SCITT Transparency Service.¶

payload:

The serialized vCon bytes, or null for detached payloads.¶

signature:

The cryptographic signature over the protected header and payload.¶

The x5chain and x5t header parameters are defined in [RFC9360].¶

B.2. The trace-metadata Map

The trace-metadata type carries summary information about the signed record in the COSE_Sign1 unprotected header. This enables consumers to inspect key properties of a signed record without deserializing the full payload.¶

The following describes each member of this map.¶

session-id:

The session identifier from the signed record.¶

agent-vendor:

The agent provider name (e.g., "anthropic", "google").¶

trace-format:

Identifies the format of the signed payload (e.g., "ietf-vac-v3.0" for canonical records).¶

timestamp-start:

When the session began.¶

timestamp-end:

When the session ended.¶

content-hash:

SHA-256 hex digest of the payload bytes, enabling integrity checking independent of the COSE signature.¶

content-hash-alg:

The hash algorithm used (default: "sha-256").¶

Editor's Note:

The label 100 for trace-metadata is a placeholder. A COSE Header Parameter registration is for further discussion.¶
